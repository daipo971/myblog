先说结论：**Decisions API 不是营销概念，实测过关。** 一次请求问 6 道题，输入 448 个 token、输出 0 个 token，端到端 0.8 秒；是非题、单选题全对；打分 3.44，手工加权验算分毫不差。但它有两个反直觉的行为，写进代码之前必须知道：答不出的题它不拒答，只给一个贴近 0.5 的低置信度概率；打分返回的是 0–4 的加权平均，不是 1–5。

背景一句话：做分类、审核、路由，过去的标准做法是调生成式模型、让它吐 JSON、再解析——慢、贵、格式还经常翻车。Google 11 月 11 日发布了 Decisions API，判题模型 `gemini-decision-1` 不生成文字，只给概率和置信度。官方说法很漂亮：一次问 1000 道题、150–250ms、输入 $0.10/百万 token、输出永远 0 token。本文不转述官方，直接拿真实 Key 调了一次，6 道题全过程贴出来，哪些说法站得住、哪些是坑，一次讲清。

## 1. 核心底层逻辑与原理解析

**判题模型和生成式模型是两种活。** 生成式模型逐 token 解码出文字；`gemini-decision-1` 是对候选答案打分，一次前向传播就出结果，不生成任何文本 token。官方文档原话：输出 token 用量永远是 0。这个设计决定了它的全部优缺点：快、便宜、格式固定，但也只能回答封闭式问题——开放式生成、结构化抽取、工具调用，Google 还是让你走 Interactions API。

**三种题型，分工很干净。**

- **noul（是非题）：** 判断一句话是否成立，返回是的概率，范围锁在 0.01–0.99，附一个置信度。适合做规则检查，比如"这条消息是不是在描述硬件故障"。
- **choice（单选题）：** 从 2–255 个固定选项里挑一个，返回胜出项和每个选项的归一化概率，总和为 1。适合路由、分流、分类。
- **score（打分题）：** 按一个有序量表打分，返回连续的加权平均分和每个等级的概率。适合给候选内容、检索片段、生成结果打分排序。

**共享输入只计费一次。** 一次请求里，一份输入（文本、图片、音频、视频、PDF，多模态可混搭）配 1–1000 道题，输入 token 只算一次，每道题只加自己的 instruction 和 criteria 的 token。上下文上限 262,144 token，输入和所有问题共享。问题之间互相隔离，加一道题不会改变其他题的答案——这对做规则引擎很关键，规则可以一条一条加，不用担心互相干扰。

**价格与限额（官方口径，11 月 12 日核对）：** 输入 $0.10/百万 token，输出 $0。免费层每分钟 200 请求、5 万 token、每天 1 万请求；付费 Tier 1 每分钟 1500 请求、100 万 token、每天 5 万请求。延迟官方称模型侧中位数 50–100ms、端到端 150–250ms，16K 上下文内、1–100 道题基本持平；还称基准套件上校准误差最低、比 Gemini 3.5 Flash-Lite 走 Interactions API 便宜近 5 倍——这两句是厂商自报，没有独立验证，本文只验证能验证的部分。

**现在只能走 Developer API。** 端点是 `v1beta`，Vertex AI 标注"即将推出"；SDK 是 `google-genai` 3.2 及以上（`client.decisions.create(...)`），OpenRouter、LangChain、Vercel AI SDK、LiteLLM、Pydantic AI、Pipecat、LiveKit、OpenCode 正在接入。OpenAI 在 10 月也上了类似的端点（GPT-6 Luna，题型叫 predicate/choice/score），两家几乎同时把"判题"做成独立产品，说明这不是一家的一时兴起，是 Agent 基础设施正在分层：生成归生成，判断归判断。

**Google 内部已经在用它当控制层。** Gemini Notebook 拿它做实时路由，按意图把查询分给不同模型档位和思考级别，日常查询延迟降 40%；Stitch 的快速画布用它秒级生成可玩的产品流程线框；Google Labs 的 CC 用它从 200 多个表情里挑反应；Google Search 把它当 MCP 工具的安全层，检测对抗行为。这些用例指向同一个结论：它的主场是 Agent 的"开关"和"分流"，不是聊天框。

## 2. 核心方案与多维对比横评

先放两张表。第一张是它和传统做法的对照：

| 维度 | Decisions API | 生成式模型 + JSON 解析 |
| :--- | :--- | :--- |
| 计费 | 只收输入，$0.10/百万 token | 输入 + 输出 + 思考 token 全收 |
| 输出 token | 永远 0 | 按生成长度收 |
| 延迟 | 官方 150–250ms；我实测端到端 0.8 秒 | 秒级，开思考更慢 |
| 返回格式 | 固定 JSON 结构 | 偶发格式翻车，要写解析重试 |
| 置信度 | 每题自带 0–1 | 得自己再调一遍或拼 logprobs |
| 适用场景 | 封闭式判题、路由、分流、打分 | 开放式生成、抽取、工具调用 |

第二张是本次实测的 6 道题。共享输入是一条中文无线耳机评价（约 150 字，提到音质、续航 6 小时、价格 299 元、耳机偏重，**没提城市、没提星期几**）：

| 题 | 类型 | 预期 | 实测 | 判定 |
| :--- | :--- | :--- | :--- | :--- |
| 是否推荐购买？ | noul | 是，高概率 | 0.958 | ✓ |
| 是否提到价格？ | noul | 是，高概率 | 0.99（封顶值） | ✓ |
| 整体情感？ | choice | 正面 | positive 0.977 | ✓ |
| 写作质量 1–5 分？ | score | 较好～很好 | 3.44（0–4 制） | ✓ |
| 是周二写的吗？ | noul | 文中无答案 | 0.431，置信度 0.569 | 不拒答，低置信度 |
| 评价者来自哪个城市？ | choice | 文中无答案 | other 0.992 | ✓（有 other 兜底）|

逐题看数字。情感单选：positive 0.977、neutral 0.018、negative 0.005，三项相加正好是 1，归一化没问题。打分题最值得展开：我给的 5 个等级是"很差、较差、一般、较好、很好"，返回的各等级概率是 4（很好）0.538、3（较好）0.384、2（一般）0.065、1（较差）0.010、0（很差）0.0025，手工加权：4×0.538 + 3×0.384 + 2×0.065 + 1×0.010 = 3.444，和返回的 3.4448 分毫不差——注意等级下标是 0–4，不是 1–5，这个换算下面避坑里细说。

两道"无答案"题是本次实测最有价值的部分。问"是不是周二写的"，文中没有任何时间信息，它没有拒答，给了 0.431，置信度 0.569——置信度的定义就是 max(noul, 1-noul)，0.569 基本等于"我不知道"。问"评价者来自哪个城市"，选项是台北、东京、首尔、other，它把 0.992 的概率压在 other 上，只给三个城市各留 0.002–0.003。结论很明确：**这个接口没有"不知道"这个输出，只有"低置信度的猜测"**，以及"有 other 兜底时它会正确地选 other"。

## 3. 手把手完整实战流程

**第一步：拿 Key。** 去 Google AI Studio 点 Get API key 就能建，不绑卡也能用免费层（每分钟 200 请求、每天 1 万请求）。提醒一句：免费层的内容会被 Google 用于改进产品，付费层不会；测敏感数据直接上付费层。

**第二步：一次 curl 调通。** 端点是 `POST https://generativelanguage.googleapis.com/v1beta/decisions`，认证用 `x-goog-api-key` 请求头。下面就是本次实测的完整请求，6 道题一次发完：

```bash
curl -X POST "https://generativelanguage.googleapis.com/v1beta/decisions" \
  -H "x-goog-api-key: $GEMINI_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "gemini-decision-1",
    "input": "这款无线耳机我用了两周，音质出乎意料地好，低音扎实，人声清晰。续航一次充电能用 6 小时，充电盒还能再充两次。价格 299 元，性价比很高。唯一缺点是耳机有点重，戴久了耳朵会累。",
    "questions": {
      "recommends": {"type": "noul", "instructions": "这条评价是否推荐购买这款产品？"},
      "mentions_price": {"type": "noul", "instructions": "评价是否提到了价格？"},
      "sentiment": {"type": "choice", "instructions": "这条评价的整体情感是？",
        "criteria": {"positive": "正面评价", "negative": "负面评价", "neutral": "中立评价"}},
      "quality_score": {"type": "score", "instructions": "按 1 到 5 分评价这条评价的写作质量",
        "criteria": ["很差", "较差", "一般", "较好", "很好"]},
      "written_tuesday": {"type": "noul", "instructions": "这条评价是否是在周二写的？"},
      "reviewer_city": {"type": "choice", "instructions": "评价者来自哪个城市？",
        "criteria": {"taipei": "台北", "tokyo": "东京", "seoul": "首尔", "other": "以上都不是"}}
    }
  }'
```

**第三步：读返回。** 本次实测 HTTP 200，端到端 0.8 秒，`usage` 是 `total_input_tokens: 448`、`total_output_tokens: 0`——0 输出 token 的说法第一次就兑现了。`answers` 按你给的问题 ID 回来，每题带 `type`、`confidence`，以及 noul 值、choice 加概率分布、或 score 加各等级概率和 `legend`（等级下标到文字的映射）。核对清单很简单：状态 200、`total_output_tokens` 等于 0、每个 `confidence` 在 0–1 之间、每个 `choice` 都在你给的选项里、`noul` 在 0.01–0.99 之间。

**第四步：换 SDK 写法。** 生产代码不用拼 curl，`google-genai` 3.2 以上直接调 `client.decisions.create(...)`，官方示例是图文混搭输入（拍一张休息室台面的照片加一句文字，同时问有没有洒水、该怎么处理、严重程度几分）。图片、视频块可以调 `resolution` 换细节换 token，媒体能内联 base64（单次请求上限 100MB）、走 Files API、或传 HTTPS 链接（每个上限 15MB）。

**第五步：算账。** 本次 448 个 token 按付费价是 $0.000045，免费层直接 0 元。按官方的估算口径，一份 2000 token 的工单加 20 道每道约 40 token 的题，一次约 2800 个输入 token，付费价约 $0.00028。做客服分流、内容审核这种量，一个月几十万次调用也在几十美元量级——前提是别把同一份输入反复发：这个端点没有缓存、没有 Batch，重复输入每次都全额计费。

## 4. 工业级避坑守则

### ⚠️ 避坑点 1：它不会说"不知道"，只会低置信度地猜
"周二写的吗"这道题实测给了 0.431、置信度 0.569。**不要把 noul 的值直接当事实用。** 正确姿势是把阈值配在置信度上：Google 的建议是按自己的标注数据定阈值，一般 0.7 以上自动走、以下转人工或走兜底。写 `if noul > 0.5` 就等于把猜测当结论。

### ⚠️ 避坑点 2：noul 封顶 0.99，"大于 0.99"永远不触发
"提到价格"那题返回正好是 0.99——不是巧合，是上下限锁在 0.01–0.99。写规则时别用 `> 0.99`，用 `>= 0.9` 这类能命中的阈值。

### ⚠️ 避坑点 3：打分返回的是 0–4 的加权平均，不是 1–5
5 个等级返回下标 0–4 的概率，加权平均 3.44 的意思是"介于较好和很好之间、更靠近很好"。官方文档写明 rubric "starting at 0"。想对外展示 1–5 分，自己加 1；直接拿 3.44 当"满分 5 分得 3.44"会低估。

### ⚠️ 避坑点 4：choice 一定要给 other 兜底
实测里有 other 它就正确集中到 other（0.992）。但官方文档明确提醒：没有兜底项时，概率会在几个错误选项间分摊。单选题务必配一个 other/catch-all，再配一道 noul 做范围检查，或者对置信度设阈值。另外注意 choice 的 key 会按字母排序，兜底项用 `other` 别用 `none_of_the_above`（后者排到最前面）。

### ⚠️ 避坑点 5：延迟看你自己的网络
官方 150–250ms 是端到端标称，我这台服务器实测 0.8 秒，差额主要在网络往返，不在模型。做实时路由、实时表情这类场景，先在自己的部署环境里测，别直接抄官方数字进 SLA。

### ⚠️ 避坑点 6：没有缓存和 Batch，重复输入每次都收费
同一份输入发两次，两次都全额计费。高频场景自己在外层做缓存：输入哈希命中就直接复用上次的答案，别每次都调接口。

### ⚠️ 避坑点 7：v1beta + Vertex 未上，生产接入留迁移余地
现在只有 Gemini Developer API 能用，Vertex AI 标注即将推出；GA 日期、区域、数据驻留条款官方都还没公布。安全过滤触发时会直接返回 HTTP 400（`safety` 或 `prohibited_content`），不是答案字段；涉及打款、封号这类高风险动作，官方自己也提醒要留人工复核——用户输入可能"为自己辩护"来争取有利分类。

## 5. 总结与后续行动建议

一句话结论：**实测过关，两个反直觉行为记牢。** 答案全对、0 输出 token 属实、共享输入一次计费属实；答不出的题它不拒答，只用低置信度告诉你它在猜；打分是 0–4 制，要自己换算。免费层每天 1 万次请求，个人测试零成本，是目前验证成本最低的一家判题接口。

上手就三步：今天去 AI Studio 拿免费 Key → 把本文的 curl 换成你自己的 5–10 道题跑一次 → 置信度 0.7 以下的走人工或兜底，跑顺了再上量。待观察三件事：GA 时间与 Vertex 上线、独立机构的校准评测、OpenAI 同类端点的价格横评。

## 常见问题

### Decisions API 能替代生成式模型做分类吗？
能替代"封闭式"分类，不能替代开放式任务。它只回答你给定的选项，不生成文字、不做抽取、不调工具。分类、路由、分流、打分、审核规则检查是它的主场；要模型写东西、抽字段、走多步推理，还是用生成式模型。

### 免费层够用吗？
个人测试完全够用：每分钟 200 请求、每天 1 万请求，本次实测一次请求 448 个 token，免费层直接 0 元。注意免费层内容会被 Google 用于改进产品，测敏感数据用付费层。

### 没有 Key 能先体验吗？
可以。Google AI Studio 里有 Doorstep Parcels、Speed Sketch、Find the Zoo Keeper 三个演示应用，不用写代码就能点一点看效果；要调接口还是得建一个 Key。

### 和 OpenAI 的 Decisions API 有什么区别？
定位几乎一样，都是"判题不生成文字"。区别在题型名字和生态：Gemini 叫 noul/choice/score，OpenAI 叫 predicate/choice/score；Gemini 目前只在 Developer API（v1beta），Vertex 还没上，OpenAI 那边 10 月就上了 GPT-6 Luna。价格横评要等两边都实测过再写，本文不展开。

## 引言

模型量化是 AI 部署优化的关键技术之一，它可以在保持模型精度的同时大幅减少模型大小和计算资源需求。说得直白一点：一个 7B 参数的大模型，用 FP16 存要占约 14GB 显存，量化到 INT4 后只要约 3.5GB，一张消费级显卡甚至一台内存够大的笔记本就能跑起来。量化不是什么黑魔法，它就是把模型权重和激活值从高精度浮点数换成低精度整数，用一点点精度换显存、速度和成本。

本文把原文的十节骨架全部保留并补实，新增三节实战内容：显存怎么算、当前主流大模型量化怎么做、精度怎么验。读完你应该能自己回答三个问题：我的硬件能跑多大的模型、该选哪种量化方法、量化完效果掉了该从哪查起。

## 1. 量化基础理论

### 1.1 量化原理

量化的核心动作只有一个：把连续的浮点数映射到离散的低精度整数上。FP32 的一个数占 4 个字节，FP16 和 BF16 占 2 个字节，INT8 占 1 个字节，INT4 只占半个字节。精度降下来，模型文件就等比变小，搬运数据的带宽压力也跟着降。

但映射不是免费的。两个浮点数本来不一样，映射到同一个整数上就分不开了，这就是量化误差。误差大小取决于两件事：数值分布是不是集中，以及量化粒度够不够细。权重分布越均匀、粒度越细，误差越小。这也是后面所有量化方法都在折腾的两件事：要么把数值分布处理得更友好，要么把粒度切得更细。

量化级别怎么选，先看一张速查表：

| 精度 | 每参数字节 | 7B 模型约占显存 | 常见用途 |
| --- | --- | --- | --- |
| FP32 | 4 | 约 28GB | 训练、科学计算 |
| FP16 / BF16 | 2 | 约 14GB | 训练、推理基准 |
| INT8 | 1 | 约 7GB | 推理部署、消费级显卡 |
| INT4 | 0.5 | 约 3.5GB | 本地部署、内存有限的设备 |

表里的数字是权重本身的估算，实际跑起来还要加上 KV 缓存、激活值和框架开销，所以要留余量，具体算法见第 11 节。

### 1.2 量化类型

均匀量化把数值区间等分成若干档，实现简单、硬件支持最好，是目前部署的主流。非均匀量化按数值密度分档，密集的地方分得细、稀疏的地方分得粗，精度更高但硬件支持少，多见于研究和专用芯片。

对称量化以 0 为中心对称映射，零点固定，计算简单；非对称量化允许零点偏移，能更好地贴合分布不对称的权重和激活值，精度略好，代价是推理时多一次零点换算。逐层量化整层共用一套参数，最省事；逐通道量化每个通道各用一套参数，粒度更细，精度损失更小，是大模型权重量化的常见选择。粒度越细，存量化参数本身的开销越大，但这笔开销和省下的权重显存比起来通常可以忽略。

## 2. 量化技术详解

### 2.1 动态量化

动态量化在推理时才实时计算激活值的量化参数，不需要提前准备校准数据，用起来最省事。PyTorch 一行代码就能做：

```python
# PyTorch动态量化
import torch
from torch.quantization import quantize_dynamic

# 动态量化模型
model_quantized = quantize_dynamic(
    model,
    {torch.nn.Linear, torch.nn.Conv2d},
    dtype=torch.qint8
)
```

它的代价是每次推理都要现场算量化参数，有额外开销，而且只量化权重和部分算子，提速幅度有限。适合的场景是：模型已经训好、不想再折腾校准流程，先快速验证 INT8 能不能用。

### 2.2 静态量化

静态量化提前用一批有代表性的数据（校准集）测出激活值的分布，推理时直接套用固定的量化参数，速度比动态量化快。PyTorch 的 FX 流程长这样：

```python
# PyTorch静态量化
import torch
from torch.quantization import quantize_fx

# 静态量化
model_prepared = prepare_fx(model, {'': default_qconfig})
model_quantized = convert_fx(model_prepared)
```

校准集是静态量化的命门：校准数据越接近真实任务的数据分布，量化后的精度保持得越好。拿随机文本去校准一个客服问答模型，效果一定打折。校准集不用很大，几百到几千条有代表性的样本通常就够了，关键是代表性，不是数量。

### 2.3 量化感知训练

量化感知训练（QAT）是在训练过程中就模拟量化误差，让模型自己学会适应低精度。它的精度保持最好，代价也最大：要重新训练，还要准备训练数据和算力。

```python
# 量化感知训练
import torch
import torch.quantization as quantization

# 定义量化配置
qconfig = quantization.get_default_qconfig('fbgemm')
model_prepared = quantization.prepare(model, qconfig)
# 训练模型
train(model_prepared)
model_quantized = quantization.convert(model_prepared)
```

一句话决策：精度要求极高、且有训练预算的场景才考虑 QAT；只是想把现成模型部署起来，后训练量化（PTQ）已经够用，不要一上来就训。

## 3. 主流框架量化支持

### 3.1 TensorFlow Lite 量化

TensorFlow Lite 是移动端和边缘设备的老牌路线，静态量化和动态量化都支持，部署到手机和开发板很成熟：

```python
# TensorFlow Lite量化
import tensorflow as tf

# 转换为TFLite模型
converter = tf.lite.TFLiteConverter.from_keras_model(model)
converter.optimizations = [tf.lite.Optimize.DEFAULT]
tflite_model = converter.convert()
```

### 3.2 ONNX Runtime 量化

ONNX Runtime 的好处是跨框架：PyTorch、TensorFlow 训出来的模型都能先转 ONNX 再量化，云端和边缘都能部署：

```python
# ONNX Runtime量化
import onnxruntime as ort
from onnxruntime.quantization import quantize_dynamic

# 动态量化
quantize_dynamic(
    "model.onnx",
    "model_quantized.onnx",
    weight_type=ort.quantization.QuantType.QUInt8
)
```

### 3.3 TensorRT 量化

TensorRT 是 NVIDIA GPU 上的推理加速路线，INT8 推理配合 Tensor Core 提速明显，但只吃 NVIDIA 的硬件，换平台就得重做：

```python
# TensorRT量化
import tensorrt as trt

# 创建量化引擎
builder = trt.Builder(TRT_LOGGER)
network = builder.create_network(1 << int(trt.NetworkDefinitionCreationFlag.EXPLICIT_BATCH))
```

选框架先看部署目标：手机和边缘设备优先 TensorFlow Lite；跨框架、多平台优先 ONNX Runtime；NVIDIA 服务器上追求极限速度优先 TensorRT；本地跑开源大模型则看第 12 节的 GGUF 路线。

## 4. 量化策略选择

### 4.1 按模型类型选择

CNN 模型权重分布相对均匀，逐通道量化通常就够了；Transformer 模型里注意力层和前馈层的数值分布差异大，混合精度量化更划算——敏感的层保持高精度，不敏感的层大胆压到低精度；RNN 模型对时序误差敏感，逐层量化配合校准数据更稳妥。没有放之四海而皆准的配方，模型的每一层对量化的敏感度都不一样，动手前先测各层的敏感度，再决定哪层压、哪层保。

### 4.2 按部署环境选择

边缘设备内存和算力都紧张，2-bit、4-bit 的极端量化才有意义，但要先确认芯片支不支持对应的低精度算子，不支持的话只是省了存储，速度未必快。云端资源相对充裕，INT8 是性价比最高的默认选择，精度损失小、生态最成熟。移动端介于两者之间，混合量化策略最常见：权重压到 INT4、激活保持 INT8，兼顾体积和精度。

## 5. 量化效果评估

### 5.1 精度评估

只看一个指标会翻车。Top-1、Top-5 准确率适合分类任务；生成任务要看在自己业务数据上的实际输出质量，光看困惑度不够；损失函数变化只能做参考，不能当结论。正确的做法是：量化前后在同一套评测集、同一套提示词上跑分，差值就是量化付出的代价。INT8 的精度损失通常很小，很多任务上几乎看不出来；INT4 在部分任务上会有可察觉的下降，能不能接受要按任务定，不能凭感觉。

### 5.2 性能评估

三个数一起看才完整：推理速度提升了多少、模型文件小了多少、运行时内存占用降了多少。注意一个常见误会：模型变小了不等于推理一定变快。低精度计算要快，前提是硬件和算子库支持对应的低精度加速；如果硬件不支持，量化只是省了显存和加载时间，计算速度可能原地踏步。评估时把三个数都测出来，别只报文件大小。

## 6. 高级量化技术

### 6.1 混合精度量化

FP16 加 INT8 的混合是最常见的组合：把对精度敏感的层留在 FP16，不敏感的层压到 INT8。动态精度调整更进一步，推理时按输入难度切换精度，简单输入走低精度、困难输入走高精度。误差补偿机制则是把上一层的量化误差记下来，在下一层里抵消一部分，层层传下去误差就不会越积越大。

### 6.2 神经架构搜索（NAS）

量化感知 NAS 把量化策略本身交给搜索算法：自动试不同的逐层精度组合，在精度和速度之间找最优解。多目标优化同时盯着精度、延迟、功耗三个目标，适合要量产落地的场景。小团队不建议一上来就搞 NAS，先把手动的逐层敏感度测明白，NAS 是有了基线之后再提效的工具。

### 6.3 知识蒸馏量化

教师模型保持高精度，学生模型在低精度下训练，目标是让学生的输出分布贴近教师。特征对齐是关键：只对齐最终输出不够，中间层的特征也要对齐，学生才学得到教师的推理方式。蒸馏加量化的组合拳，在小模型上效果尤其明显——一个 INT4 的小模型，蒸馏得好可以接近 FP16 中模型的表现。

## 7. 实际应用案例

### 7.1 图像分类模型量化

ResNet 量化到 INT8 后精度损失通常在 1 个百分点以内，是量化最成熟的场景。MobileNet 本来就是为移动端设计的轻量模型，量化优化的重点是深度可分离卷积层的逐通道参数，压得好可以在几乎不掉精度的情况下把模型压到几 MB。自定义量化策略的思路都一样：先测敏感度，再定每层的精度，最后在目标硬件上实测验证。

### 7.2 目标检测模型量化

YOLO 和 SSD 量化时要特别注意检测头：分类分支对量化不敏感，回归分支（框的位置）对量化更敏感，两个分支用同一套精度容易顾此失彼。常见做法是主干网络压到 INT8，检测头保持 FP16，精度和速度都能保住。

### 7.3 自然语言处理模型量化

BERT 量化是 NLP 量化的入门案例，INT8 下精度保持得很好。Transformer 量化真正的难点在注意力机制：注意力分数的数值范围大、分布尖锐，直接量化容易丢信息，AWQ 这类激活感知的方法就是为了解决这个问题。语义保留策略的核心是校准数据要用真实语料，不要用随机生成的文本，否则量化后的模型在真实任务上掉点会比评测集上看到的大。

### 8.1 量化工具对比

| 工具 | 支持框架 | 量化类型 | 部署平台 |
| --- | --- | --- | --- |
| PyTorch | PyTorch | 动态/静态 | 多平台 |
| TensorFlow Lite | TensorFlow | 静态 | 移动端/边缘 |
| ONNX Runtime | 多框架 | 动态/静态 | 云端/边缘 |
| TensorRT | 多框架 | 静态 | NVIDIA GPU |
| llama.cpp / GGUF | 开源大模型 | 权重量化 | CPU、消费级显卡 |

最后一行是给想自己微调的人准备的：bitsandbytes 的 4-bit 量化配合 QLoRA，可以在一张消费级显卡上微调 7B 模型，训练时省显存，推理时再用正常流程部署。

### 8.2 自定义量化工具

自己搭量化工具链要备三件东西：和目标任务分布一致的校准数据集、按层记录精度配置的配置管理、量化前后自动跑评测并出对比报告的结果分析。缺了第三件，量化就变成凭感觉调参数，出了问题只能从头再来。

## 9. 量化挑战与解决方案

### 9.1 精度损失问题

精度掉了先别急着换方法，按顺序查三件事：校准数据对不对、敏感层有没有被误压、量化粒度够不够细。多数精度问题出在前两件上。量化感知训练、知识蒸馏、误差补偿是三件套，按成本从低到高排：先试误差补偿和粒度调整，再试蒸馏，最后才上 QAT。

### 9.2 硬件兼容性问题

硬件特定的量化格式是落地时最容易踩的坑：同一个 INT8 模型，在 A 芯片上跑得飞快，在 B 芯片上可能根本跑不起来。跨平台量化要先确认目标硬件支持的算子清单，再选量化格式；硬件加速支持不是想当然，动手前查官方文档里那张支持列表，比事后调试省时间得多。

## 10. 未来发展趋势

### 10.1 超低精度量化

1-bit 量化和二值神经网络把压缩推到极限，研究上已经能跑，但通用任务的精度还不够，离大规模落地还有距离。现阶段的实用建议是：把 1-bit 当技术跟踪，不要当选型依据；真正要部署的，INT4 是目前的下限。

### 10.2 硬件协同设计

专用量化硬件、神经形态计算都在往"为低精度而生"的方向走，硬件和算法一起设计，量化就不再是事后补救，而是从一开始就长在模型里。量子量化还处在概念阶段，知道有这么个方向就够了。

## 11. 显存算账：先算再下模型（2026-11-20 新增）

动手之前先算一笔账，公式只有一行：

```text
权重大约占显存 = 参数量 × 每参数字节数
```

7B 模型 FP16 约 14GB、INT8 约 7GB、INT4 约 3.5GB，前面第 1 节的表就是这么来的。但这只是权重，跑起来还要加三笔：KV 缓存（上下文越长、并发越高，占得越多，长上下文时可能超过权重本身）、激活值和框架开销（一般再留 20% 到 30% 的余量）。所以 16GB 显存的显卡跑 INT4 的 7B 模型是舒服的，跑 INT8 的 7B 就要看上下文长度；8GB 显存想跑 7B，基本只能选 INT4，还要把上下文截短。

决策流程就三步：先看手里硬件的可用显存，再按公式倒推能装多大的模型，最后按任务精度要求定 INT8 还是 INT4。顺序不要反——先下模型再发现装不下，是最浪费时间的。

## 12. 大模型量化实战：GPTQ、AWQ 与 GGUF（2026-11-20 新增）

现在最常见的场景不是量化一个自己训的分类模型，而是把开源大模型量化后在本地跑起来。三条路线覆盖了绝大多数需求：

**GPTQ**是后训练权重量化的经典方法，逐层做误差补偿，不需要重新训练，只需要一小批校准数据。优点是通用、生态成熟，缺点是量化过程本身比较慢，大模型要跑上一段时间。

**AWQ**是激活感知权重量化，思路是先看激活值，找出那些数值特别大的"显著通道"，重点保护这些通道对应的权重。实测中 AWQ 在 INT4 下的精度保持通常比朴素的均匀量化更好，尤其适合 Transformer 模型。

**GGUF**是 llama.cpp 的模型格式，也是本地部署最省事的路线：模型发布者已经提供量化好的 GGUF 文件，Q4_K_M 是最常用的档位，精度和体积的平衡点。Ollama 和 LM Studio 底层走的都是这条路线，下载即用，不用自己跑量化流程。自己动手量化的顺序建议是：先直接用现成的 GGUF 档位跑起来，效果不够再试 AWQ 或 GPTQ 自己量化，QAT 排在最后。

长上下文场景还有一笔账要算：KV 缓存量化。主流推理框架支持把 KV 缓存也压到低精度，长上下文、多并发时省下的显存很可观；短上下文、单人使用时收益不大，可以先不管。

## 13. 精度验证与避坑清单（2026-11-20 新增）

量化完不要只看文件变小了，按这张清单验一遍再上线：

- **同一套评测集前后对比**：量化前后用同一套数据、同一套提示词跑分，差值就是代价，不要拿量化后的分数去比原模型官方报告里的分数。
- **看真实任务，不只看榜单**：榜单分数没掉不等于业务没掉，拿自己业务里最难的二十个真实问题跑一遍，人工看输出。
- **校准数据要像真实数据**：校准集和业务数据的分布越接近，精度保持越好；分布差得远，评测集上的分数会骗人。
- **2-bit 先别碰**：极端量化现阶段只适合研究和特定硬件，通用部署的下限是 INT4。
- **先确认硬件支持再选格式**：低精度要提速，硬件和算子库必须支持对应的加速；不支持的话，量化只省显存不提速。
- **商用前看许可证**：开源模型的权重许可证各有条件，本地自己用和对外提供服务的要求不一样，商用前读一遍许可证原文。

## 常见问题

**16GB 显存的电脑能跑多大的模型？** INT4 的 7B 到 8B 模型比较舒服，INT8 的 7B 要看上下文长度，13B 以上建议上 INT4 或者换更大显存。先按第 11 节的公式算，再下模型。

**INT8 和 INT4 怎么选？** 精度优先选 INT8，显存不够再退到 INT4。INT8 的精度损失通常很小，INT4 在部分任务上会有可察觉的下降，决定之前先在自己的任务上跑一遍对比。

**Ollama 下载的模型已经是量化过的吗？** 是的，Ollama 默认拉取的通常是 Q4_K_M 之类的量化档位，开箱即用。想换档位可以在拉取时指定标签，不用自己跑量化流程。

**量化后模型变小了，为什么推理没变快？** 两个可能：一是硬件或算子库不支持对应的低精度加速，量化只省了显存；二是瓶颈不在计算而在显存带宽或 KV 缓存，这时要配合 KV 缓存量化或者缩短上下文。先定位瓶颈再动手。

## 总结

| 层次 | 关注点 | 关键实践 |
| --- | --- | --- |
| **原理层** | 精度与体积的交换 | 按参数量乘字节数算显存，留 20% 到 30% 余量 |
| **方法层** | GPTQ、AWQ、动态/静态量化 | 后训练量化优先，QAT 只在精度要求极高时用 |
| **部署层** | 框架与硬件匹配 | 移动端 TensorFlow Lite，跨平台 ONNX，本地大模型 GGUF |
| **验证层** | 同一套评测集前后对比 | 真实任务抽查，校准数据贴近业务分布 |
| **避坑层** | 硬件支持与许可证 | 先查算子支持列表，商用前读许可证原文 |

量化不是越低越好，而是在精度、显存、速度三者之间找到适合自己硬件和任务的平衡点。先算账、再选方法、最后验证，这三步走完，量化才算真正落地。

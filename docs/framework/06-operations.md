# 06 运营流程

## 节奏总表

| 周期 | 做什么 | 谁做 |
| --- | --- | --- |
| 每天 | 扫信息源（下表），把值得写的事件记进 backlog 的「快讯候选」；重大新闻 48 小时内出快讯 | AI 可做 |
| 每周 | 中文 3 篇（常青 2 + 快讯 1），英文 1–2 篇；快讯要点并入档案页；Telegram 精选 1 次 | AI 写，站长抽查 |
| 每月 1 日 | 更新价格表 / 数据页；检查海外服务通关的风控变化；跑一次全站死链和自检脚本 | AI 可做 |
| 每月 | 数据复盘（[08-metrics.md](08-metrics.md)）：找出要更新、合并、补强的文章 | AI 出报告，站长拍板 |
| 每季度 | 更新对比和合集；重排 backlog 优先级；更新选题地图的覆盖列；复盘目标 | AI 出方案，站长拍板 |
| 每年 | 常青文章标题年份更新；定位和目标复盘 | 站长 |

## 每周排期模板

| 星期 | 内容 |
| --- | --- |
| 周一 | 常青 1（从 backlog P0 / P1 领） |
| 周三 | 快讯 1（本周最重要的事件；没有重大事件就换成档案页更新） |
| 周五 | 常青 2 + 英文 1 篇 |
| 周日 | 本周快讯并入档案页；更新中心页；Telegram 本周精选 |

发布时间建议北京时间早上 8–10 点（front matter 的 `date` 用 `+08:00`，且不能晚于实际推送时间，否则 Hugo 不会生成页面）。

## 信息源

快讯必须有一手来源。按可信度排序，优先引用前两层。

| 层级 | 来源 | 例子 |
| --- | --- | --- |
| 一手 | 官方博客 / 公告 / 文档 | openai.com/news、anthropic.com/news、blog.google、deepseek 官方公众号与 api-docs、moonshot 平台公告、minimax 官网新闻、阶跃星辰官网 |
| 一手 | 官方代码与权重 | GitHub 组织页（deepseek-ai、MoonshotAI、MiniMax-AI、stepfun-ai、QwenLM、THUDM）、Hugging Face 组织页 |
| 一手 | 论文 | arXiv、官方技术报告 |
| 一手 | 官方社交账号 | 各公司 X / 微博 / 公众号官方号 |
| 二手可信 | 专业媒体 | 机器之心、量子位、36氪、TechNode、The Verge、TechCrunch、MarkTechPost |
| 数据 | 第三方榜单和价格 | LMArena、Artificial Analysis、OpenRouter 模型页、Vals.ai |
| 线索 | 社区 | X、Reddit r/LocalLLaMA、Hacker News、V2EX、即刻 —— 只作线索，不作来源 |

规则：

- 只有社区爆料、没有官方或可信媒体确认的消息，不写快讯，最多在 Telegram 提一句并标「未证实」。
- 引用的链接必须真实存在、亲自打开过或来自搜索结果原文；不编造网址。
- 第三方跑分写明来源和日期。

## 快讯筛选标准

满足任意一条才写成文章：

1. 国内用户能直接用上的新模型或新功能。
2. 价格、免费额度明显变化。
3. 国内可用性、风控、支付渠道变化。
4. 开放权重的重要模型发布（参数、许可证）。
5. 行业大事件（头部公司上市、重大并购、重大政策）。

不写：小版本更新、融资新闻、人事变动、纯营销活动（这些可以只发 Telegram）。

## 分发渠道

| 渠道 | 方式 | 优先级 | 说明 |
| --- | --- | --- | --- |
| 搜索引擎 | 自然收录 + IndexNow | 最高 | 一切的基础 |
| Telegram 频道 | `tg-push.yml` 新文自动推送；每周手动发精选 | 高 | 二次触达、复访 |
| X（Twitter） | 新文和档案页更新发帖，中英各自账号 | 中 | 英文端主要社交渠道；不用自动关注、刷量 |
| 知乎 / 小红书 | 回答高频问题，引用本站文章 | 低 | 只在有精力时做，内容必须针对平台重写 |
| 邮件通讯 | 每周精选 | 规划中 | 流量稳定后再做（见路线图） |

仓库根目录有一些旧的推广脚本（`auto-twitter-*.sh`、`xhs-publish.sh` 等）和 WORKFLOW.md，是早期尝试，不属于本框架的标准流程。使用前先确认符合平台规则，避免账号风险。

## 读者反馈闭环

- 评论区（自托管评论后端）和 Telegram 里的提问：每周汇总一次，能写成 FAQ 的加进对应文章，频繁出现的问题进 backlog。
- 读者指出错误：48 小时内核实，改正并在更新记录写明。
